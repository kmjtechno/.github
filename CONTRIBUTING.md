# Contributing to KMJ TECHNO projects

Thank you for helping improve verifiable, secure engineering tools.

1. **Choose the appropriate repository.** Check its README, license, release readiness, existing issues and any repository-specific contribution instructions. These defaults apply only where a project has not defined its own policy.
2. **Describe the problem first.** Include expected behavior, actual behavior, affected version/commit and a sanitized reproduction. Large design changes should be discussed with the maintainers before implementation.
3. **Keep changes focused.** Work on a separate branch, preserve backwards compatibility and do not bypass authorization, user consent, safety gates, licensing or release controls.
4. **Add evidence.** Include tests, reproducible steps, static checks and screenshots only when needed. State what could not be verified; never mark a test as passed when it did not run.
5. **Protect data and infrastructure.** Do not commit API keys, personal data, private repo content, production backups or credentials. Use example configurations and local test data instead.
6. **Use pull requests.** Summarize the purpose, key files, exact checks run, risks and rollback needs. Maintainers decide whether/when a change is accepted.
7. **Show changes quickly, but truthfully.** Follow the [KMJ Fast Live Visibility policy](docs/FAST-LIVE-VISIBILITY.md): push focused commits promptly, share exact-head CI and preview/build artifacts, and promote only verified, authorized immutable releases. Distinguish PR visibility, preview, staging and production—never claim a PR merge made the customer site live. Preserve free-first operation and release safety.

Please use private vulnerability reporting for security issues rather than ordinary pull requests or public issues. Engineering projects may be in research, preview or gated-release phases; do not advertise unfinished capabilities as publicly available.
